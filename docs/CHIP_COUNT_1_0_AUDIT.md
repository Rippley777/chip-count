# Chip Count 1.0 audit

## Executive summary

**Chip Count is approximately 77% ready as a focused 1.0 product, and approximately 30% ready for Mac App Store submission.** The analytics engine is substantial and tested. The remaining work is mostly correctness at the presentation boundary, resilient startup, native usability, and an App Store distribution path.

| 🟡 PARTIAL                 |       11 |
| 🔴 MISSING                 |        0 |
| 💥 BROKEN                  |        0 |

These are whole-feature classifications. Zero missing/broken features does **not** mean there are no missing capabilities or confirmed defects: calendar week/month presets, persistent sandbox file permissions, model session counts, and native Settings are absent; chart rankings and calendar presentation have defects. Those sit inside otherwise functioning, partial features. Unverified sub-behaviors are identified below rather than classifying an entire functioning feature as unverified.

Readiness is an engineering estimate, not a measured probability of approval. The product score is the rounded mean of the per-feature progress estimates below. The App Store estimate also accounts for distribution requirements outside the 15-feature list. Passing an unsandboxed build is not proof of App Store readiness.

The five most important things preventing shipment are:

1. **No App Sandbox implementation or durable permission to read user-selected session roots.** Current discovery and watchers depend on unrestricted filesystem paths. Stored path strings do not preserve sandbox permission across restart.
2. **No true Today / This Week / This Month reporting flow.** Today exists, but the other presets are rolling ranges. Reporting defaults to UTC instead of initializing from the user's timezone.
3. **Charts can misrepresent time and omit the largest sessions.** Empty time buckets disappear; the activity calendar compresses missing days; highest-usage sessions are selected from the first paginated response.
4. **Startup/index failures lack a safe recovery experience.** Database setup failure terminates startup; low-level errors can reach the UI. There is no inspect/retry/recover flow that preserves notes and settings.
5. **The submission package and listing are unfinished.** Existing automation requires Developer ID signing and notarization, not App Store distribution. Entitlements, provisioning, App Store packaging/validation, final screenshots, listing/support/privacy material, and final native acceptance checks remain.

**Recommendation:** finish this as a local, read-only Claude Code/Codex usage viewer. Preserve the working pricing and export engine. Do not expand into account billing, cloud sync, productivity scoring, or elaborate forecasts before 1.0.

Audit date: **October 4, 2026, America/Chicago**. Repository: `/Users/allyrippley/Code/2027/chip-count`, commit `c14a676`, initially clean. README and screenshot changes appeared concurrently during the audit and were preserved; the final report accounts for those assets. No product implementation was changed by this audit. Builds/tests generated ignored outputs; a temporary audit probe was used for verification.

## Accounting, pricing and date findings

The canonical formula is:

```text
total = uncached_input + output_including_reasoning + cache_read + cache_write
cost  = (input * input_rate + output * output_rate
       + cache_read * read_rate + cache_write * write_rate) / 1,000,000
```

Reasoning is an output subset, not an additional throughput/cost category. Codex's reported input includes cache categories; `Counters::usage` subtracts these into disjoint canonical categories. Claude's categories are already disjoint. Cumulative counters are differenced and reconciled with strong response identities; corrections replace snapshots rather than accumulate twice. Own usage is aggregated globally; carry-in and parent rollups are retained separately. Explicit child contributions can be displayed without global double counting.

Rates are converted to integer arithmetic and rounded once per event to nanodollars; sums use stored integer `nano` values before converting to display dollars. Events retain pricing versions. Overrides affect new observations; explicit repricing changes history. Auto-review mapping is marked inferred in events, totals, exports and most UI cost labels. Unsupported service tiers, Claude fast mode and one-hour cache writes remain unpriced unless overridden.

Spot checks against the current [OpenAI pricing table](https://developers.openai.com/api/docs/pricing) agreed with bundled Astra, Sol 6.1 and Luna standard categories and long-context multipliers. The six bundled Claude families agree with the current [Claude standard/cache pricing table](https://platform.claude.com/docs/en/about-claude/pricing). These checks support the existing catalog; they do not verify every legacy/auto-review contract or guarantee future prices. Newer Claude identifiers are absent from the bundled catalog and remain safely unpriced until configured. Before release, recheck every supported identifier and the long-context threshold against its model documentation, keeping provenance and historical versions.

Date-only filters resolve midnight in the configured IANA timezone; end dates include that calendar day by using the next midnight as an exclusive bound. ISO filters use their timestamp instants. DST regressions cover 23-hour and repeated-hour Chicago days. Prior-period comparison subtracts an equal absolute duration, not a calendar week/month; all-time correctly has no invented prior baseline. Session duration uses lifetime first/last metadata even if token totals are filtered to a smaller interval. This should be labeled explicitly.

## Local data and privacy

The normal unsandboxed macOS native location resolves to `~/Library/Application Support/labs.rippley.chip-count/chip-count.sqlite`; native code asks Tauri for the application-data directory. The development bridge uses `dirs::data_local_dir()` with the same identifier. Both support an explicit data-directory override. App Sandbox changes the permitted container/location; that variant is not implemented.

SQLite stores `sources`, durable `files` offsets/fingerprints/parser state, `sessions`, canonical `events` with integer cost, `origins`, `markers`, `annotations`, `projects`, `budgets`, `alerts`, provider `limits`, current `prices`, versioned pricing/settings `config`, and `schema_version`. It stores usage metadata, paths, IDs, labels and user notes, not transcript bodies or tool arguments. Retention removes usage events and obsolete origins; other metadata/checkpoints persist. Reducing retention then extending it will not automatically re-import deleted historical events from unchanged checkpointed files; the user needs a rebuild.

Native `notified-alerts.json` persists delivered-alert identities, and the window-state plugin persists geometry. UI page/filter/selection/columns/saved views/inspector dimensions use WebView localStorage, separately from SQLite. Browser demo sessions use a separate in-memory engine; demo metadata and synthetic context values are explicitly marked and do not populate the real index.

No login, API key, external analytics, cloud database, remote font fetch, or transcript upload is needed. Production uses embedded Rust through `dispatch`; `/api/*` is a loopback development bridge only. Its host/origin/body validation has tests. Release scripts contact Apple only when explicitly run for release operations. Prices contain source URLs as metadata; those are not automatic network fetches.

## Ship Blockers

### 1. Make source access work in App Sandbox

Add an App Store-specific config/entitlements/provisioning path. Introduce native user selection that stores read-only security-scoped bookmarks, resolves/reopens them on launch, handles stale/revoked access, and holds access during scans/watchers. Keep JSONL reads strictly read-only. Raw entered paths and home-directory auto-discovery cannot substitute for permission in this build.

Apple requires sandboxing for Mac App Store apps. Its filesystem guidance explains durable security-scoped bookmarks and balanced access calls. This is a direct gap between the required platform model and `Engine::discover`, `pickPath`, stored `sources.path`, and `start_monitor`; it has not been proven by running a sandboxed build. See [Apple review guideline 2.4.5](https://developer.apple.com/app-store/review/guidelines/) and [Apple sandbox file access](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox).

The current launch-at-login plugin uses a LaunchAgent. Disable this optional control in the App Store 1.0 build until a supported sandbox-compatible implementation is verified. Test native save and Finder reveal inside the sandbox too; canonical-path validation is not an OS permission grant.

**Acceptance:** sandboxed build can select supported roots, restart, append/rotate logs, survive sleep/wake, revoke/regrant access, show unavailable roots, save an export, and leave source content unchanged. An Apple reviewer can reach useful data through a clear demo/onboarding flow without installing a development environment.

### 2. Deliver calendar reporting with honest time boundaries

Move calendar period resolution into Rust/shared explicit metadata. Initialize a fresh workspace with the detected IANA timezone, allow override, and show timezone plus actual range. Implement Today, This Week and This Month, choose/document week start, and distinguish to-date comparisons from complete prior periods. Use one filter interpretation for cards, charts, sessions and export.

**Acceptance:** day/week/month/year rollover, leap day, Chicago DST and a second non-US timezone; sessions spanning midnight contribute only their in-range events. A fresh Chicago install does not silently use UTC's day.

### 3. Correct the chart claims that can change interpretation

Fix daily/minute time spacing and zero days, align the calendar or remove it, correct the Live sparkline label and cost legend, and derive global top sessions from the full filtered backend view. Do not add new charts until these are right.

**Acceptance:** sparse fixture containing a month-long gap stays spatially honest; the large old session from the audit probe appears in the global ranking; token chart categories equal the canonical total; cost charts visibly disclose partial/inferred estimates.

### 4. Provide recoverable errors and keyboard-complete primary flows

Introduce structured user-facing error categories at the IPC boundary. Handle unavailable/corrupt index setup with a native recovery screen/dialog rather than terminating before React loads. Preserve the existing database and metadata before any user-requested recovery; never silently rebuild or discard notes. Supply retry/reselect/source diagnostics and neutral cancellation handling.

Finish native Settings/Cmd-comma and useful Help, reliable keyboard session selection/paging and dialog focus return. Add an equivalent button/table/date-input path for any primary action otherwise reachable only by clicking a chart. Retain default macOS edit/window behavior.

**Acceptance:** inaccessible source, malformed JSONL, corrupt SQLite, failed save, invalid rate/timezone and cancelled dialogs result in understandable next steps; keyboard alone can configure a source, inspect/filter history, change settings and export. Rebuild/upgrade preserves notes, prices and budgets.

### 5. Produce and verify the actual submission deliverables

Keep the Developer ID/notarization workflow for direct distribution; add a separate App Store build and signed installer-package workflow using the proper distribution credentials/provisioning. Current `macos-release.mjs` explicitly rejects other identities, so it cannot be reused unchanged. Tauri documents a separate [App Store workflow](https://v2.tauri.app/distribute/app-store/) with sandbox entitlements, provisioning and `.pkg` packaging.

Align release versions/build numbers, verify the final signed artifact's entitlements and identifiers, and test the exact artifact intended for submission. Prepare screenshots at currently accepted dimensions, accurate description, support/privacy URLs/material, privacy declarations and reviewer instructions. App Store Connect account/listing state was not inspected and must be confirmed; it is not inferred absent merely because it is outside this repo.

**Acceptance:** validated App Store package, sandboxed first-run/restart/native dialogs on supported Macs, consistent final metadata, and a review-ready listing. Apple processing/review time is outside the engineering estimate.

## Architecture Concerns

1. **Full-history processing before pagination.** `Engine::events` deserializes all enabled events; `view` clones/filters them and walks session relationships. `snapshot` can call another full `view` for previous-period comparison. Detail, compare, export, budgets and tray queries add more full-history work. Pagination bounds the response/DOM, not backend memory or aggregate CPU. Push bounded selection/aggregation into indexed SQL or cache validated aggregates incrementally as history grows; preserve accounting semantics.
2. **Duplicated refresh triggers.** Main/compact windows poll every 3 seconds; native emits `index-updated` after each monitor pass, even unchanged data, and listeners query again. The native monitor itself also builds a full snapshot. A shared revision/dirty notification with serialized/coalesced refresh can reduce repeated work and contention on `Mutex<Engine>`. Browser monitoring is a separate implementation.
3. **Traversal's budget is soft.** Each source directory walk precedes ingestion and can exceed the 750 ms reconciliation budget. Every pass can revisit a large directory tree; count/depth caps prevent unlimited traversal but do not prove low idle CPU. File batches and rotating cursors are good existing protections.
4. **Frontend coupling.** `src/App.tsx` is 5,126 lines and `styles.css` 4,368 lines. Page orchestration, storage, shortcuts, export state, charts and settings are intertwined. Extract focused period, error, session-navigation and native-menu adapters as touched; avoid a whole-app refactor before release.
5. **UI derives facts from a paginated response.** Highest-session rankings, model selector options, command search and comparison candidates use `snapshot.sessions`. Backend global totals are correct, but those UI lists are not global. Return global selector/ranking metadata independently of session pagination.
6. **JSON-heavy persistence and migration gap.** Most tables store `data` blobs; a schema_version table is seeded without version checks or sequential upgrades. Add explicit migration/backup/restore behavior before changing the durable schema for sandbox bookmarks or richer metadata. Backward-compatible serde defaults already help additive event fields.
7. **Pricing is centralized but tier rules are code.** Long-context thresholds/multipliers, service warnings, aliases and rate arrays span parser/pricing responsibilities. This is manageable now; document supported basis and use a richer registry later. Catalog seed skips existing IDs, so changing a tuple will not update existing installations automatically.
8. **Retention and source changes leave auxiliary metadata.** Usage retention/source removal hide or delete derived usage differently; sessions, file states, markers/limits and annotations can outlive it. Document this and bound cleanup without removing user notes. Increasing retention needs an intentional historical rebuild.
9. **Native startup and OS behavior are tightly coupled to unrestricted paths.** Source discovery assumes home/environment roots; reveal launches platform file-manager commands; login launch registers a LaunchAgent. App Sandbox needs a genuine permission abstraction and an explicit supported native feature subset, not only a plist switch.
10. **Platform support is overstated by configuration alone.** macOS 11 minimum and cross-platform branches exist, but this audit built only the current Mac architecture/OS. Verify the minimum supported macOS version, Intel/universal artifact and plugin/API compatibility, or narrow the documented support range honestly.

## Recommended 1.0 Scope

**Strict definition:** Chip Count 1.0 is a stable, sandboxed, offline macOS app that reads user-authorized local Claude Code and Codex usage logs and explains current/recent sessions, calendar-period token usage, model contributions and honest API-equivalent costs. It preserves local preferences/notes, has usable native menus and keyboard flows, and ships with a validated App Store package and accurate listing. It never promises invoice/account completeness or inferred human working time.

### MUST SHIP IN 1.0

- Durable sandbox source selection, restart access, revoked-access recovery and strictly read-only logs.
- Current/most-recent session visibility with latest model, category tokens, estimated cost, first/last observation and clearly labeled activity/span.
- Today, This Week and This Month with visible reporting timezone/range, correct boundaries, session counts and the same filtered accounting throughout.
- Tested canonical own-usage accounting, model token breakdown/drill-down, versioned centralized pricing, useful overrides and explicit unknown/inferred estimates.
- Searchable/sortable/paged session history and useful inspector, with keyboard access to core actions.
- One truthful daily token/cost trend, model contribution view and optional session trend; correct sparse time and complete-history ranking wherever shown.
- Local persistence, safe upgrades, startup/index failure recovery and source diagnostics without raw internals.
- Native About/Settings/edit/window/Help/quit behavior, standard Command shortcuts and sufficient dark/light contrast/focus.
- Existing CSV/JSON export verified in the sandbox if retained. Do not spend 1.0 time adding export variants.
- Consistent existing-quality icon, curated screenshots, supported-platform validation and exact signed App Store submission artifact/listing.

### SHIP IF EASY

- Aggregate model cost/session-count columns, original-model-ID disclosure and better range-aware filenames.
- Recent dollars/min with explicit sample/coverage; safe, clearly labeled local budget thresholds.
- Fix the activity calendar only if it is quick; otherwise remove it from the release surface.
- Keep existing Projects, Compare and compact monitor if they pass final acceptance without creating new scope. Hide failing secondary workflows instead of expanding them.
- Basic refresh coalescing/revision checks and scan-progress copy while touching the relevant code.

### MOVE TO 1.1+

- Unusual-day detection, end-of-period forecasts, sophisticated pacing and additional charts.
- Expanded comparison/project management, advanced calendar visualization and new export variants.
- Optional login launch/notifications until their sandbox native behavior is verified.
- Cloud sync, account/billing reconciliation, quota reconstruction, remote pricing feeds, ecosystem integrations and cross-device totals.
- Large-scale persistence redesign, multi-million-event claims and Windows/Linux releases.

No missing optional feature should hold up this release. Correct local accounting, authorized file access, honest reporting, recoverability and a verified submission package define the launch bar.
